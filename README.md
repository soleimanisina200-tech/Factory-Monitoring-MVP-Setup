# سامانه‌ی پایش صنعتی کارخانه

شناسایی هویت کارکنان (با یونیفرم مشابه)، زمان حضور در منطقه‌ها، عبور جهت‌دار از خطوط و مناطق، ایمنی راننده‌ی لیفتراک و پشتیبانی از چند دوربین.

این راهنما برای کسی نوشته شده که سامانه را **نصب، پیکربندی و بهره‌برداری** می‌کند. اگر اولین بار است پروژه را باز می‌کنید، بخش‌های ۳ تا ۸ را به ترتیب انجام دهید.

## ۱. این سامانه چه می‌کند

| قابلیت | توضیح |
|---|---|
| **هویت کارکنان** | هر فرد یک شماره (ID) می‌گیرد و آن را هنگام پنهان‌شدن پشت مانع، عبور از کنار دیگران و **خروج و ورود دوباره به تصویر** نگه می‌دارد. |
| **یونیفرم مشابه** | سامانه خودش یاد می‌گیرد «دو کارگر متفاوت در این کارخانه چقدر شبیه هم دیده می‌شوند» و سخت‌گیری‌اش را با آن تنظیم می‌کند؛ در تردید، **ID جدید** می‌دهد نه ID اشتباه. برای هویت قطعی، **نشانگر روی کلاه** (اختیاری) پشتیبانی می‌شود. |
| **منطقه‌ها** | چه کسی در کدام منطقه است، از چه زمانی، و مجموعاً چه مدت (چند بار ورود، مجموع ثانیه). منطقه‌ی ممنوعه، سقف مدت حضور و سقف تعداد نفر. |
| **خطوط و مناطق جهت‌دار** | چه کسی از کدام خط یا دروازه، در کدام جهت عبور کرد. مسیر یک‌طرفه (هشدار عبور خلاف جهت). |
| **لیفتراک و راننده** | تشخیص راننده‌ی هر لیفتراک (حتی وقتی **سقف کابین** او را پنهان می‌کند)، مدت نشستن پشت لیفتراک، هشدار وقتی راننده پیاده شود و دور شود یا از تصویر بیرون برود. |
| **چند دوربین** | هر دوربین پردازش مستقل خودش را دارد و یک دفتر مشترک، همان فرد را در همه‌ی دوربین‌ها با یک **شماره‌ی شخص (P)** می‌شناسد. |
| **ثبت و گزارش** | همه‌ی رویدادها در یک پایگاه‌داده (SQLite) + CSV + عکس لحظه‌ی هشدار؛ گزارش روزانه به تفکیک هر کارگر. |
| **بهره‌برداری صنعتی** | اتصال دوباره‌ی خودکار به دوربین، ادامه‌ی کار پس از خطای یک فریم، ذخیره‌ی هویت‌ها بین ری‌استارت‌ها، لاگ چرخشی، فایل سلامت (heartbeat)، خروجی هشدار به webhook / MQTT. |

**اصل طراحی:** دادن ID اشتباه به یک نفر بدتر از دادن ID جدید است. هر جا شواهد کافی نباشد، سامانه محتاطانه عمل می‌کند و تصمیم را در لاگ توضیح می‌دهد.

## ۴. نصب

### ۴-۱. محیط Python
```powershell
cd <مسیر پروژه>
conda create -y -p .\env python=3.10
conda activate .\env
```
این فعال‌سازی را در هر ترمینال جدید تکرار کنید.

### ۴-۲. PyTorch نسخه‌ی CUDA
دستور ساده‌ی `pip install torch` روی ویندوز نسخه‌ی **CPU** نصب می‌کند. به https://pytorch.org/get-started/locally/ بروید، گزینه‌های *Stable / Windows / Pip / Python / جدیدترین CUDA* را انتخاب و دستور نمایش‌داده‌شده را اجرا کنید؛ شکل کلی:
```powershell
pip install torch torchvision --index-url https://download.pytorch.org/whl/cuXXX
```

### ۴-۳. بقیه‌ی وابستگی‌ها
```powershell
pip install -r requirements-dev.txt
```
اگر نصب `torchreid` خطا داد، آن را از مخزن GitHub پروژه‌ی deep-person-reid نصب کنید. برای خروجی هشدار MQTT: `pip install paho-mqtt` (اختیاری).

### ۴-۴. بررسی نصب
```powershell
python scripts/diagnostic.py
pytest -q
```
`diagnostic.py` بسته‌ها، CUDA، فایل تنظیمات، کالیبراسیون، صحنه و مدل لیفتراک را بررسی می‌کند و برای هر مورد `OK` / `WARN` / `FAIL` می‌نویسد. همه‌ی تست‌ها باید `passed` باشند.

### ۴-۵. وزن مدل‌ها (خودکار در اولین اجرا)

| فایل | کاربرد |
|---|---|
| `yolo11m-pose.pt` | تشخیص افراد و اسکلت |
| `yolo11m.pt` | تشخیص وسیله (تا وقتی مدل اختصاصی لیفتراک ندارید) |
| `weights/osnet_x1_0_msmt17.pt` | ویژگی ظاهری (Re-ID) |

وزن Re-ID ابتدا از Google Drive و در صورت شکست (که زیاد پیش می‌آید) **خودکار از مخزن رسمی نویسنده در Hugging Face** (`kaiyangzhou/osnet`) دانلود می‌شود. همین سازوکار برای `osnet_ain_x1_0` و `osnet_ibn_x1_0` هم کار می‌کند. اگر سرور به اینترنت دسترسی ندارد، فایل را روی سیستم دیگری دانلود و در پوشه‌ی `weights\` با همان نام بگذارید. وزنی که با مدل انتخاب‌شده جور نباشد در شروع رد می‌شود.

## ۶. کالیبراسیون کف زمین

**چرا لازم است:** فاصله‌ی راننده تا لیفتراک (متر)، سرعت افراد و بخشی از منطق هویت به تبدیل «پیکسل به متر» وابسته‌اند. بدون کالیبراسیون، **هشدار فاصله معتبر نیست**.

1. روی زمین یک **مستطیل** انتخاب کنید که چهار گوشه‌اش در تصویر دیده شود (خطوط کف، کاشی‌ها) و هرچه بزرگ‌تر بهتر.
2. طول و عرض واقعی آن را با متر اندازه بگیرید.
3. اجرا کنید:
   ```powershell
   python scripts/calibrate_ground_plane.py --source data/input/clip1.mp4 --width-m 6 --length-m 8
   ```
   `--width-m` فاصله‌ی گوشه‌ی ۱ تا ۲ و `--length-m` فاصله‌ی گوشه‌ی ۲ تا ۳ است.
4. چهار گوشه را **ساعت‌گرد** کلیک کنید: بالا-چپ ← بالا-راست ← پایین-راست ← پایین-چپ. کلیدها: `s` ذخیره، `r` از نو، `q` خروج.

نتیجه در `configs/calibration.yaml` ذخیره می‌شود (برای چند دوربین با `--out` مسیر هر دوربین را بدهید). رزولوشن تصویر هم ذخیره می‌شود و اگر رزولوشن استریم عوض شود نقاط خودکار مقیاس می‌گیرند.

**بررسی درستی:** در `draw_zone.py` با کلید `v` تصویر از بالا با شبکه‌ی ۱ متری نمایش داده می‌شود؛ خطوط کف باید صاف و اندازه‌ها واقعی باشند. در اجرای اصلی هم دور هر لیفتراک «رد کف» آن و فاصله‌ی راننده به متر رسم می‌شود؛ با یک فاصله‌ی معلوم مقایسه کنید.

**هر بار دوربین جابه‌جا شد یا زاویه‌اش تغییر کرد، کالیبراسیون و صحنه را دوباره انجام دهید.**

## ۷. تعریف صحنه

همه‌ی شکل‌ها در `configs/scene.yaml` ذخیره می‌شوند (نه در `settings.yaml`؛ توضیحات فایل تنظیمات دیگر پاک نمی‌شود). رزولوشنی که شکل‌ها روی آن رسم شده‌اند (`image_wh`) ذخیره می‌شود و همه‌چیز به رزولوشن استریم مقیاس می‌گیرد.

### ۷-۱. منطقه‌ها و درها
```powershell
python scripts/draw_zone.py --source data/input/clip1.mp4
```

| کلید | کار |
|---|---|
| `SPACE` | ثابت‌کردن فریم برای رسم |
| کلیک چپ / راست | افزودن نقطه / برگرداندن آخرین نقطه |
| `t` | نوع شکل بعدی: `presence` (حضور) ← `restricted` (ممنوعه) ← `exit_door` (در خروج) |
| `ENTER` | بستن چندضلعی و نام‌گذاری |
| `d` | حذف آخرین شکل |
| `TAB` یا `m` | رفتن به حالت کالیبراسیون (۴ نقطه + ابعاد) و برگشت |
| `v` | پیش‌نمایش کالیبراسیون (شبکه‌ی ۱ متری) |
| `s` / `q` | ذخیره / خروج |

- **منطقه‌ی حضور (`presence`)**: زمان حضور هر کارگر ثبت می‌شود.
- **منطقه‌ی ممنوعه (`restricted`)**: ورود هر فرد = هشدار `ZONE_INTRUSION`.
- **در خروج (`exit_door`)**: دری که **داخل تصویر** است (نه لبه‌ی تصویر). کسی که آنجا ناپدید شود «خارج‌شده» حساب می‌شود و بازگشتش فقط از همان‌جا (یا لبه‌ی تصویر) پذیرفته می‌شود. اگر درِ ورود و خروج کارگران وسط تصویر است، حتماً آن را رسم کنید.

محدودیت‌های هر منطقه را دستی در `scene.yaml` بنویسید:
```yaml
zones:
  loading_dock: {polygon: [...], type: presence, max_dwell_sec: 1800, max_occupancy: 4}
```

### ۷-۲. خط عبور (tripwire)
```powershell
python scripts/draw_line.py --mode line --name main_gate --labels IN OUT
```
نقطه‌ی A و B را کلیک کنید. فلش سبز جهت برچسب اول (`IN`) را نشان می‌دهد؛ `i` آن را برعکس می‌کند. `s` ذخیره.

### ۷-۳. منطقه‌ی جهت‌دار (دروازه)
```powershell
python scripts/draw_line.py --mode region --name entrance --labels IN OUT
```
سه گوشه یا بیشتر را کلیک کنید، `d` را بزنید و دو نقطه **از بیرون به داخل** برای فلش ورود کلیک کنید. `s` ذخیره.

### ۷-۴. مسیر یک‌طرفه
```powershell
python scripts/draw_line.py --mode line --name corridor --allowed IN
```
عبور در جهت دیگر رویداد `WRONG_WAY` می‌سازد.

| `--vehicle-config` | تنظیمات لیفتراک؛ اگر فایل نباشد یا `enabled: false`، ماژول لیفتراک خاموش است |
| `--calibration` | فایل کالیبراسیون (پیش‌فرض `configs/calibration.yaml`) |
| `--output مسیر.mp4` | محل ذخیره‌ی ویدیوی خروجی؛ بدون آن: `outputs/<نام ویدیو>_annotated.mp4` (بخش ۱۴-۴) |
| `--no-gui` | بدون پنجره‌ی نمایش (حالت سرویس) |
| `--set بخش.کلید=مقدار` | تغییر یک تنظیم فقط برای همین اجرا، مثلاً `--set reid.reentry_sim_thresh=0.85` (قابل تکرار) |
| `--max-frames N` | توقف پس از N فریم (تست و سنجش سرعت) |
| `--restart-on-failure` | دوربین زنده: پس از خطای مهلک، خط پردازش از نو ساخته شود |
| `--cameras` / `--camera-id` | اجرای یک دوربین از فهرست چند دوربین (بخش ۱۳) |

**در ابتدای لاگ بررسی کنید:**

| خط | معنی |
|---|---|
| `Using cuda:0: NVIDIA ...` | GPU فعال است |
| `Ground calibration loaded from ...` | کالیبراسیون اعمال شده |
| `Re-ID backbone osnet_x1_0: weights ... (100% of layers matched)` | مدل Re-ID درست است |
| `Scene: 2 zones, 1 lines, 0 regions, 1 exit doors` | صحنه خوانده شده |
| `Vehicle classes: ['0:forklift']` | مدل لیفتراک و کلاس آن |

**توقف:** کلید `q` در پنجره، یا `Ctrl+C`. هنگام توقف، رویدادهای در صف نوشته و هویت‌ها ذخیره می‌شوند.

**پایان اجرا:** با تمام‌شدن ویدیو، فایل خروجی بسته می‌شود و مسیر آن در لاگ (`Annotated video will be saved to ...`) آمده است. اگر با `q` یا `Ctrl+C` زودتر متوقف کنید، ویدیو تا همان لحظه ذخیره است.

## ۹. شناسایی هویت کارکنان

### ۹-۱. چگونه کار می‌کند
- تا وقتی فرد در تصویر است، **ردیاب** او را دنبال می‌کند و مدیر هویت هر چند دهم ثانیه با ظاهر (OSNet روی بدن + بالاتنه/سر + رنگ) کنترل می‌کند که ردیاب روی فرد دیگری نپریده باشد.
- وقتی فرد **پشت مانع** (کامیون، دستگاه، لیفتراک) پنهان می‌شود، تا `occlusion_max_sec` (پیش‌فرض ۵ دقیقه، مثلاً برای بارگیری) «فعال» می‌ماند و نباید ID جدید بگیرد:
  - می‌تواند هر جای همان مانع بیرون بیاید، تا فاصله‌ی `physics_bev.max_internal_occlusion_m` (پیش‌فرض ۱۵ متر، یعنی طول یک کامیون) و با سرعت راه‌رفتن.
  - فرد تازه‌ای که جایی ظاهر شود که یک فرد پنهان ممکن است از آنجا بیرون بیاید، تا `emerge_wait_sec` (۲ ثانیه) ID جدید نمی‌گیرد. در این مدت تصویرهای نیمه‌پنهانِ کنار مانع کنار می‌روند و تصمیم با تصویر تمیز گرفته می‌شود.
  - مقایسه‌ی «نفر دوم» فقط با کسانی است که واقعاً می‌توانند همین فرد باشند. افرادی که الان جای دیگری دیده می‌شوند، یا از لبه‌ی تصویر خارج شده‌اند، دیگر جلوی بازیابی را نمی‌گیرند.
  - اگر دو نفر پشت یک مانع بروند، هر کدام با ظاهر خودش به ID خودش برمی‌گردد. اگر ظاهرشان قابل‌تشخیص نباشد، ID جدید داده می‌شود و ادغام اشتباه انجام نمی‌شود.
- وقتی از **لبه‌ی تصویر** (با حرکت به بیرون) یا از یک **درِ داخل تصویر** خارج می‌شود، «خارج‌شده» ثبت می‌شود. از آن پس فقط از «دروازه‌ی سخت‌گیر ورود دوباره» می‌تواند ID‌اش را پس بگیرد: چند نمونه‌ی تمیز، شباهت بالاتر از آستانه، و فاصله‌ی کافی با نفر دوم.
- اگر فرد برگشتی اول ID جدید گرفت و بعد شواهد قوی شد، دو ID **ادغام** می‌شوند و همه‌ی گزارش‌ها به ID قدیمی منتسب می‌شود.

### ۹-۲. یونیفرم مشابه: آستانه‌ی خودتنظیم
با لباس فرم، شباهت ظاهری دو کارگر **متفاوت** بسیار بالاتر از حالت عادی است؛ آستانه‌ی ثابت (مثلاً ۰٫۸۲) باعث می‌شود تازه‌واردی که یونیفرم مشابه دارد ID فردِ خارج‌شده را بگیرد.

سامانه هر بار که دو کارگر **هم‌زمان و جدا از هم** در تصویرند، شباهتشان را به‌عنوان نمونه‌ی «دو نفر متفاوت» جمع می‌کند و آستانه‌ی ورود دوباره را این‌گونه می‌گذارد:

```
آستانه = بیشینه( reentry_sim_thresh ، صدک ۹۹٫۵ شباهتِ افرادِ متفاوت + ۰٫۰۳ )   (حداکثر ۰٫۹۵)
```

مقدار فعلی در نوار بالای تصویر (`re-entry thr`) و در `/api/status` دیده می‌شود. همین آستانه برای پنهان‌شدن‌های طولانی داخل صحنه (بیش از `recover_strict_after_sec`) هم اعمال می‌شود.

**نتیجه‌ی عملی:** در کارخانه‌ای با یونیفرم کاملاً یکسان و تصویر دور، بازگشت بعد از غیبت طولانی اغلب **ID جدید** می‌گیرد (نه ID اشتباه). اگر به هویت قطعی و پایدار نیاز دارید از نشانگر کلاه/جلیقه استفاده کنید.

تنظیم پیشنهادی برای محیط تمام‌یونیفرم (رنگ لباس اطلاعات کمی دارد، سر و بالاتنه بیشتر):
```yaml
reid: {head_branch_weight: 0.45, color_branch_weight: 0.10}
```
اثر آن را با روش بخش ۱۸ روی ویدیوی خودتان بسنجید.

### ۹-۳. نشانگر روی جلیقه یا کلاه (هویت قطعی، اختیاری)
یک نشانگر چاپی (ArUco) روی **جلیقه** (سینه و پشت) یا **کلاه** هر کارگر، ارزان‌ترین راه هویت قطعی با دوربین ثابت است. تنها راهی است که دو کارگر **هم‌لباس و هم‌قد** را از هم جدا می‌کند.

**نحوه‌ی کار:**
- **وصل‌شدن:** با دو بار خواندن نشانگر در چند ثانیه، فرد به هویتِ همان نشانگر وصل می‌شود. این حتی وقتی کار می‌کند که ظاهرش عوض شده باشد، بعد از ری‌استارت، و در دوربین‌های دیگر.
- **قاطع بودن:** دو هویت با نشانگر متفاوت **هرگز** ادغام یا با هم اشتباه نمی‌شوند. نام کارگر در تصویر و گزارش‌ها می‌آید.
- **بیرون‌آمدن از پشت مانع:**
  - **نشانگر دیگر:** کسی که پس از پنهان‌شدن (مثلاً پشت کامیون) با ID فرد پنهان بازیابی شده ولی نشانگر **دیگری** دارد، همان لحظه ID خودش را می‌گیرد. فرد پنهان دقیقاً به حالت قبلی برمی‌گردد (`MARKER_REBIND`).
  - **نشانگر قبلاً خوانده نشده:** اگر نشانگر فرد پنهان قبلاً هرگز خوانده نشده بود، معلوم نیست این همان فرد است یا هم‌لباسِ دیگری. نشانگر فقط به **همین رد** نسبت داده می‌شود و سابقه‌ی قبلی به اسم کسی ثبت نمی‌شود (`MARKER_SPLIT`).
  - **هزینه‌ی این احتیاط:** اگر واقعاً همان فرد بوده، سابقه‌ی قبلی‌اش با شماره‌ی جدا و بدون نام می‌ماند. پس نشانگر باید طوری نصب شود که **از اولِ دیده‌شدن** خوانده شود.

**جا و اندازه:**
- **جست‌وجو:** نشانگر در دو ناحیه جست‌وجو می‌شود: سر (`head`) برای کلاه و تنه (`torso`، بین شانه و لگن) برای جلیقه. هر دو پیش‌فرض فعال‌اند (`markers.regions`).
- **حداقل اندازه در تصویر:** نشانگر باید دست‌کم حدود **۲۴ پیکسل** عرض داشته باشد. اندازه‌ی لازم برای دوربین خودتان را اسکریپت حساب می‌کند:

| دوربین 1080p، لنز ۹۰ درجه | اندازه‌ی لازم | جا |
|---|---|---|
| تا ۳ متر | حدود ۸ سانتی‌متر | کلاه |
| تا ۸ متر | حدود ۲۰ سانتی‌متر | جلیقه (سینه + پشت) |
| تا ۱۰ متر | حدود ۲۵ سانتی‌متر | جلیقه |
| بیشتر | بزرگ‌تر از قابل‌پوشیدن | دوربین 4K (نصف اندازه)، لنز باریک‌تر، یا دوربین نزدیک‌تر |

```powershell
# اندازه برای دوربین شما را حساب می‌کند و فایل‌های چاپی می‌سازد
python scripts/make_markers.py --ids 1-40 --distance-m 8 --image-width 1920 --hfov-deg 90 --out markers
Copy-Item configs\workers.example.yaml configs\workers.yaml               # سپس فهرست کارکنان را پر کنید
```
```yaml
# configs/workers.yaml
dictionary: DICT_4X4_50          # ۴×۴ = خانه‌های بزرگ‌تر = خوانا از فاصله‌ی دورتر
workers:
  - {marker_id: 7, name: "علی رضایی", employee_id: "E-1043"}
```
```yaml
# configs/settings.yaml
markers: {enabled: true, regions: [head, torso]}
```

**نکات نصب:**
- **دو طرف جلیقه:** روی هر کارگر **یک شماره** به کار ببرید، روی سینه و پشت جلیقه. از بغل خوانده نمی‌شود، ولی کافی است یک بار در چند ثانیه دیده شود.
- **جنس:** نشانگر باید **مات و صاف** باشد: دوخته یا لمینیت‌شده. نشانگرِ چروک، خمیده یا براق خوانده نمی‌شود.
- **حاشیه:** حاشیه‌ی سفید دور نشانگر را نپوشانید، برای تشخیص لازم است.
- **آزمایش:** قبل از تهیه برای همه، چند نمونه را در دورترین نقطه‌ی دید هر دوربین امتحان کنید. در `logs/identity_decisions.jsonl` دنبال `LABELED` بگردید.

### ۹-۴. ماندگاری هویت‌ها
برای دوربین زنده، هویت‌ها هر دقیقه و هنگام توقف در `data/identity_store/<camera_id>/` ذخیره می‌شوند. پس از ری‌استارت:
- شماره‌ها از ۱ شروع **نمی‌شوند** (گزارش‌ها قاطی نمی‌شوند)؛
- افراد قبلی به‌عنوان «خارج‌شده» بارگذاری می‌شوند و فقط از دروازه‌ی سخت‌گیر (یا نشانگر) برمی‌گردند.

برای فایل ویدیو این قابلیت پیش‌فرض خاموش است (اجرای دوباره‌ی یک کلیپ نباید آن را «به یاد بیاورد»). کلید: `reid.persistence.mode: auto | on | off`.

### ۹-۵. قد نسبی (مستقل از یونیفرم و نور)
با یونیفرم یکسان، ظاهر دو کارگر به هم نزدیک است، ولی قدشان معمولاً نه: دو نفر تصادفی به‌طور معمول حدود ۱۰ سانتی‌متر اختلاف قد دارند.

**نحوه‌ی کار:**
- **بدون کالیبراسیون:** روی کف صاف، قد پیکسلی یک فرد تقریباً تابعی خطی از جای پاهایش در تصویر است. هر دوربین این رابطه را از عبور خود افراد **یاد می‌گیرد**.
- **قد نسبی هر نفر:** نسبت قد اندازه‌گیری‌شده به قد مورد انتظار در آن نقطه، یعنی ۱٫۰۰ برای کارگر متوسط و ۱٫۰۵ برای ۵٪ بلندتر. میانه‌ی چند ثانیه محاسبه می‌شود.
- **کدام فریم‌ها:** فقط وقتی فرد **ایستاده و کامل** دیده می‌شود. یعنی مچ، زانو، لگن، شانه و سر دیده شوند، پای تکیه‌گاه صاف باشد، تنه عمودی باشد، دست بالای سر نباشد، با کسی هم‌پوشانی نداشته باشد و لبه‌ی تصویر او را نبریده باشد. هنگام راه‌رفتن هم اندازه‌گیری می‌شود.
- **فقط برای رد کردن:** اختلاف واضح قد یعنی دو نفر متفاوت. قد یکسان چیزی را ثابت نمی‌کند.
- **کاربرد:** در همه‌ی تصمیم‌ها استفاده می‌شود: بازیابی پس از پنهان‌شدن، ورود دوباره، ادغام خودکار و پیوند بین دوربین‌ها.
- **پیوند موقت:** کسی که پس از پنهان‌شدن (مثلاً پشت کامیون) بازیابی می‌شود، تا قدش اندازه‌گیری شود پیوند **موقت** دارد و گالری ظاهرِ فرد پنهان از او یاد نمی‌گیرد. اگر قدش آشکارا متفاوت بود، پیوند لغو می‌شود (`BINDING_BROKEN`، `reason: STATURE`)، وضعیت فرد پنهان بازگردانده می‌شود و فرد بیرون‌آمده ID خودش را می‌گیرد.

**دقت و محدودیت:**
- حدود یک‌چهارم تا ۴۰٪ از جفت کارگرهای هم‌لباس را با اطمینان جدا می‌کند، یعنی آن‌هایی که حدود ۸ سانتی‌متر یا بیشتر اختلاف قد دارند.
- خطای اندازه‌گیری هر نفر در محاسبه لحاظ می‌شود: کسی که اندازه‌هایش پراکنده است، هرگز کسی را رد نمی‌کند.
- روی کلیپ آزمایشی، خطای هر نفر بین ۰٫۵ تا ۴٪ بود. روی ویدیوی کارخانه دوباره بسنجید.

تنظیم‌ها در `reid.stature` (بخش ۱۶).

### ۹-۶. آموزش مدل ظاهر روی ویدیوی کارخانه‌ی خودتان
مدل عمومی OSNet روی عابران با لباس‌های گوناگون آموزش دیده است. با یونیفرم یکسان، شباهت دو کارگر متفاوت به حدود ۰٫۸۵ می‌رسد. مدلی که روی ویدیوی **همین کارخانه** آموزش ببیند، جزئیاتی را یاد می‌گیرد که واقعاً فرق دارند: صورت و مو، کفش، فرم بدن و طرز پوشیدن لباس.

**برچسب‌زدن دستی لازم نیست:**
- **مثبت‌ها:** تصویرهای یک بخش تمیز از یک رد، یعنی یک نفر و بدون هم‌پوشانی با کسی.
- **منفی‌ها:** کسانی که **هم‌زمان** در یک فریم دیده می‌شوند، حتماً دو نفرند. در کارخانه همین‌ها سخت‌ترین جفت‌ها هستند: هم‌لباس و زیر یک نور.

```powershell
# ۱) جمع‌آوری داده از ویدیوهای ضبط‌شده‌ی دوربین‌های واقعی (چند ساعت، روزها و شیفت‌های مختلف)
python scripts/mine_reid_data.py --source D:/rec/cam1_day1.mp4 D:/rec/cam1_day2.mp4 D:/rec/cam2_day1.mp4 --out data/reid_mining
# ۲) آموزش و سنجش (کل ویدیوها برای ارزیابی کنار گذاشته می‌شوند)
python scripts/train_reid.py --data data/reid_mining
# فقط سنجش یک مدل روی همان داده:
python scripts/train_reid.py --data data/reid_mining --eval-only --weights weights/osnet_x1_0_site.pt
```

خروجی، قبل و بعد از آموزش و روی ویدیوهای کنارگذاشته، این‌ها را نشان می‌دهد:
- `threshold`: آستانه‌ای که ۹۹٫۵٪ جفت‌های **دو کارگر متفاوت** را رد می‌کند. همان آستانه‌ای است که بخش ۹-۲ یاد می‌گیرد.
- `genuine_accept`: سهم جفت‌های **یک نفر** که از آن آستانه رد می‌شوند. **عددی است که باید بالا برود.**
- `eer`: نرخ خطای برابر.

**استفاده:** فقط اگر `genuine_accept` آشکارا بهتر شد، در `settings.yaml` این را بگذارید:
```yaml
reid: {weights_path: weights/osnet_x1_0_site.pt}
```
`model_name` باید همان قبلی بماند. اگر هیچ دوره‌ای بهتر نشد، اسکریپت مدل را ذخیره نمی‌کند و مدل فعلی می‌ماند.

**نکته‌ها:**
- **حجم داده:** چند ساعت ویدیو با چند نفر هم‌زمان در تصویر لازم است.
- **GPU:** آموزش روی RTX 4090 برای چند ساعت ویدیو معمولاً کمتر از یک ساعت طول می‌کشد.
- **حریم خصوصی:** پوشه‌ی `data/reid_mining` تصویر کارکنان را دارد. مثل خودِ ضبط‌ها از آن محافظت کنید (در git ثبت نمی‌شود).
- **بعد از عوض‌کردن مدل:** حافظه‌ی ظاهری ذخیره‌شده‌ی هویت‌ها خودبه‌خود کنار گذاشته می‌شود (بخش ۹-۴).

## ۱۰. منطقه‌ها

برای هر (کارگر، منطقه):

| رخداد | شرط |
|---|---|
| `ZONE_ENTER` | نقطه‌ی پا `entry_confirm_sec` داخل بماند (زمان ورود = اولین لحظه‌ی داخل) |
| `ZONE_EXIT` | `exit_confirm_sec` بیرون بماند (مدت = تا اولین لحظه‌ی بیرون)؛ `reason: WALKED_OUT` |
| `ZONE_EXIT` با `LOST` | داخل منطقه `lost_timeout_sec` دیده نشود (مدت تا آخرین مشاهده) |
| `ZONE_EXIT` با `LEFT_CAMERA` | مدیر هویت اعلام کند فرد از تصویر خارج شده |
| `ZONE_EXIT` با `SHUTDOWN` | سامانه متوقف شود در حالی که فرد هنوز داخل است (حضورِ در جریان گم نمی‌شود) |

- مجموع هر کارگر (تعداد دفعات و مجموع ثانیه) نگه داشته می‌شود و در گزارش می‌آید.
- لرزش چند پیکسلی نقطه‌ی پا روی مرز، حضور را دو تکه نمی‌کند.
- فردی که هنوز ID ندارد هم شمرده می‌شود و رویدادش وقتی ID گرفت به او منتسب می‌شود (`zones.include_unverified`).
- قواعد: `type: restricted` ← `ZONE_INTRUSION` (هشدار)؛ `max_dwell_sec` ← `ZONE_DWELL_EXCEEDED`؛ `max_occupancy` ← `ZONE_OVER_CAPACITY`.

## ۱۱. خطوط و مناطق جهت‌دار

**خط:** به‌جای «برخورد پاره‌خط‌ها»، سمتِ پایدارِ فرد نسبت به خط نگه داشته می‌شود و یک **نوار مرده** (`dead_band_px`) دور خط نادیده گرفته می‌شود. عبور یعنی تغییر سمت پایدار. بنابراین:
- کسی که **روی خط ایستاده** و نقطه‌ی پایش می‌لرزد، ورود/خروج پیاپی نمی‌سازد؛
- عبوری که بین دو سر خط نباشد شمرده نمی‌شود؛
- اگر فرد هنگام عبور لحظه‌ای پنهان شود (تا `max_gap_sec`) عبور همچنان شمرده می‌شود.

**منطقه‌ی جهت‌دار:** هنگام ورود به چندضلعی نقطه‌ی ورود ذخیره و هنگام خروج، جابه‌جایی با بردار ورود مقایسه می‌شود (حداقل `min_displacement_px`). کسی که **داخل منطقه ناپدید شود** (از دری که داخل آن است بیرون برود) هم با آخرین نقطه‌اش ارزیابی و شمرده می‌شود. پرسه‌زدن داخل منطقه عبور حساب نمی‌شود.

**انتساب به کارگر:** اگر کسی در ثانیه‌ی اول حضورش (قبل از گرفتن ID) از خط بگذرد، رویداد تا `attribution.timeout_sec` نگه داشته و با ID درست ثبت می‌شود؛ اگر ID نگیرد، «ناشناس» ثبت می‌شود (نه اینکه گم شود).

## ۱۲. لیفتراک و راننده

### ۱۲-۱. مدل تشخیص لیفتراک (پیش‌نیاز بهره‌برداری)
مدل عمومی COCO کلاس «لیفتراک» **ندارد**. تنظیم پیش‌فرض (`yolo11m.pt`، کلاس ۷ = کامیون) فقط برای راه‌اندازی اولیه است. تشخیص راننده از بقیه بدون یک مدل لیفتراکِ قابل‌اعتماد ممکن نیست، پس این مهم‌ترین قدم بخش لیفتراک است:

```powershell
# ۱) استخراج فریم‌های ارزشمند (فریم‌های تکراری صحنه‌ی ثابت کنار گذاشته می‌شوند)
python scripts/prepare_vehicle_dataset.py extract --source D:/rec/cam1.mp4 D:/rec/cam2.mp4 --out data/forklift_dataset --every-sec 2
#    اختیاری: پیش‌برچسب از یک مدل YOLO (فقط برای سرعت؛ باید اصلاح شود)
#    --prelabel yolo11m.pt --prelabel-classes truck
# ۲) برچسب‌زدن در CVAT / Label Studio / Roboflow با قالب YOLO، کلاس ۰ = forklift
#    نتیجه در data/forklift_dataset/labeled/images و .../labeled/labels
# ۳) بررسی برچسب‌ها و تقسیم (کل ویدیوها برای ارزیابی کنار گذاشته می‌شوند)
python scripts/prepare_vehicle_dataset.py split --out data/forklift_dataset --names forklift
# ۴) آموزش و سنجش
python scripts/train_vehicle_model.py --data data/forklift_dataset/data.yaml
```

**برچسب‌زدن:**
- **چندضلعی (segmentation) بهتر است:** لبه‌ی واقعی شاسی روی زمین را می‌دهد و فاصله‌ی راننده تا لیفتراک دقیق‌تر می‌شود. اسکریپت خودش مدل `-seg` را انتخاب می‌کند. جعبه هم کار می‌کند.
- **تنوع:** لیفتراک با و بدون سقف، با بار و بدون بار، همه‌ی زاویه‌ها و دوربین‌ها، روز و شب. حداقل حدود ۲۰۰ تصویرِ دارای لیفتراک لازم است.
- **تصویر منفی:** تصویر بدون لیفتراک باید فایل `.txt` **خالی** داشته باشد. این تصویرها به مدل یاد می‌دهند پالت، کامیون و قفسه لیفتراک نیستند.
- **بررسی خودکار:** مرحله‌ی `split` شماره‌ی کلاس، تعداد مختصات، نرمال‌بودن و فایل‌های جاافتاده را بررسی می‌کند و خطا را با اسم فایل می‌گوید.

**نتیجه:**
- **سنجه‌ها:** precision، recall و mAP روی ویدیوهای کنارگذاشته چاپ می‌شوند.
- **recall مهم‌ترین عدد برای ایمنی است.** لیفتراکی که دیده نشود، هشدار هم ندارد. زیر ۰٫۹۰ هشدار داده می‌شود.
- **تنظیم:** در پایان، خطوط لازم برای `configs/vehicle_monitoring.yaml` چاپ می‌شوند:
```yaml
vehicle_detector_weights: weights/forklift_yolo11m-seg.pt
vehicle_class_names: [forklift]
vehicle_class_ids: []
```

### ۱۲-۲. راننده چگونه تعیین می‌شود
همه‌ی زمان‌ها بر حسب **ثانیه** است (مستقل از سرعت پردازش).

| وضعیت | قاعده |
|---|---|
| **دیده‌شدن در کابین** | فردی که بدنش در ناحیه‌ی کابین است: لیفتراک پارک ← `board_confirm_sec`؛ حالت نشسته‌ی واضح ← `seated_board_confirm_sec`؛ لیفتراک در حرکت ← باید **همراه آن** حرکت کند (`moving_board_confirm_sec`). عابری که لیفتراک از جلویش رد می‌شود راننده نمی‌شود. |
| **یک نفر، یک لیفتراک** | هر فرد فقط راننده‌ی یک لیفتراک است؛ با سوار شدن به لیفتراک دیگر، جلسه‌ی قبلی بسته می‌شود. |
| **تعویض راننده** | اگر راننده‌ی ثبت‌شده بیرون باشد و فرد دیگری در کابین تأیید شود، جلسه‌ی قبلی بسته (`DRIVER_CHANGED`) و هشدارش پاک می‌شود. |
| **تغییر شماره‌ی ردیاب** | اگر شماره‌ی راننده عوض شود ولی همان بدن همان‌جا باشد، اتصال حفظ می‌شود. ادغام هویت‌ها هم به ماژول لیفتراک اعلام می‌شود. |

### ۱۲-۳. لیفتراک سقف‌دار (راننده پنهان)
سقف و ستون‌های کابین، از دید دوربینِ بالا، راننده را کامل یا ناقص پنهان می‌کنند. قواعد:

| موقعیت | رفتار |
|---|---|
| راننده سوار شده و زیر سقف دیده نمی‌شود | همچنان `DRIVER_ONBOARD` (برچسب `hidden/roof`) و زمان نشستن شمرده می‌شود؛ **هشدار نمی‌دهد**. |
| فردی کنار/داخل کابین ناپدید می‌شود و لیفتراک راه می‌افتد | همان فرد راننده است (`VANISHED_INTO_CAB`). اگر دو نفر هم‌زمان آنجا ناپدید شده باشند، **حدس زده نمی‌شود**. |
| لیفتراک حرکت می‌کند و هیچ راننده‌ای شناخته نیست | `OCCUPIED_UNKNOWN_DRIVER` (کسی پنهان در حال رانندگی است؛ هرگز «پارک، بدون راننده» نشان داده نمی‌شود). |
| فرد **جدیدی** درست کنار لیفتراکِ پارک‌شده‌ای که راننده‌ی پنهان داشت ظاهر می‌شود | راننده‌ی در حال پیاده‌شدن است (`EMERGED_FROM_CAB`) و از همان لحظه فاصله‌اش پایش می‌شود. |
| بدن راننده ناقص دیده می‌شود | امتیاز کابین از مفصل‌های دیده‌شده و هم‌پوشانی کادر محاسبه می‌شود (به دیدن کامل بدن نیاز ندارد). |

محدودیت ذاتی: کسی که **پشت** لیفتراکِ پارک‌شده ایستاده (پاهایش پشت بدنه پنهان است) از یک دوربین قابل تمایز از راننده‌ی نشسته نیست. سامانه برای این حالت زمان تأیید کامل می‌خواهد و اگر لیفتراک راه بیفتد و آن فرد همراهش نرود، اتصال را بدون هشدار باز می‌کند. زاویه‌ی دوربینی که داخل کابین را ببیند این ابهام را کم می‌کند.

### ۱۲-۴. فاصله و هشدار

| وضعیت (رنگ کادر) | معنی |
|---|---|
| `UNASSIGNED` (خاکستری) | پارک، بدون سرنشین شناخته‌شده |
| `OCCUPIED_UNKNOWN_DRIVER` (آبی) | سرنشین پنهان و ناشناس |
| `DRIVER_ONBOARD` (سبز) | راننده در کابین (دیده یا پنهان) |
| `DRIVER_EXITED_SAFE` (فیروزه‌ای) | پیاده شده، نزدیک لیفتراک |
| `DRIVER_EXITED_WARNING` (نارنجی) | بین حد هشدار و حد مجاز |
| `DISTANCE_VIOLATION_ALARM` (قرمز) | **راننده بیش از حد مجاز دور شده** |
| `DISTANCE_UNCERTAIN` (سرخابی) | پای راننده دیده نمی‌شود؛ فاصله تقریبی است |
| `DRIVER_NOT_VISIBLE` (بنفش) | پیاده شده و کنار لیفتراک دیده نمی‌شود |
| `DRIVER_LEFT_VIEW_ALARM` / `DRIVER_NOT_VISIBLE_ALARM` (قرمز تیره) | راننده‌ی پیاده‌شده از تصویر خارج شده / مدت زیادی ناپیداست |

- **فاصله** بین نقطه‌ی پای راننده و «رد کف» لیفتراک به متر است. رد کف از لبه‌ی پایینی وسیله (که روی زمین است) ساخته و به اندازه‌ی `vehicle_depth_m` به سمت دور از دوربین امتداد داده می‌شود.
- **هشدار فاصله** وقتی است که فاصله بیش از `safe_distance_threshold_m` به مدت `alarm_confirm_sec` باشد (یک فریم نویزی هشدار نمی‌سازد) و با برگشتن به داخل (حد مجاز منهای `clear_hysteresis_m`) به مدت `alarm_clear_sec` پاک می‌شود (`DRIVER_ALARM_CLEARED`).
- **فاصله‌ی نامطمئن** (پا پنهان): هیچ‌وقت هشدار را پاک نمی‌کند و فقط وقتی هشدار می‌دهد که فاصله از حد مجاز + `uncertain_margin_m` بیشتر باشد.
- **خروج راننده از تصویر** پس از پیاده‌شدن = لیفتراک بی‌متصدی ← `DRIVER_LEFT_VIEW_ALARM` (کلید `alarm_on_driver_left_view`).
- **سیاست هشدار** (`alarm_on_driver_left_view`، `driver_lost_alarm_sec`، حدهای فاصله) را با مسئول ایمنی کارخانه نهایی کنید.

### ۱۲-۵. مدت نشستن پشت لیفتراک
هر «جلسه» از سوار شدن تا پایان (تعویض راننده، رفتن به لیفتراک دیگر، خروج لیفتراک از تصویر، `session_timeout_sec` دوری، یا توقف سامانه) است. `DRIVER_EXITED` مدت همان نوبت نشستن و `DRIVER_SESSION_END` مجموع ثانیه‌های نشستن جلسه را دارد؛ زمانی که راننده زیر سقف پنهان است هم شمرده می‌شود. جمع هر کارگر در `forklift_sessions.csv` و `workers.csv` می‌آید.

## ۱۳. چند دوربین

### ۱۳-۱. طرح کلی
- هر دوربین در **فرایند مستقل** خودش اجرا می‌شود (تشخیص، ردیاب و ID‌های محلی خودش). خرابی یک دوربین بقیه را متوقف نمی‌کند و ناظر آن را دوباره راه می‌اندازد.
- یک **دفتر مشترک** (`data/cross_camera.db`) هویت‌های محلی همه‌ی دوربین‌ها را نگه می‌دارد و به هر فرد یک **شماره‌ی شخص `P`** می‌دهد که در همه‌ی دوربین‌ها یکی است.
- رویدادهای همه‌ی دوربین‌ها در **یک پایگاه‌داده** (ستون `camera_id`) ثبت می‌شود و گزارش، فعالیت هر شخص را از همه‌ی دوربین‌ها جمع می‌کند.

### ۱۳-۲. قواعد پیوند بین دوربین‌ها (به ترتیب اعتبار)
1. **نشانگر کلاه/جلیقه**: همان نشانگر = همان شخص، قطعی.
2. **فیزیک و قد**: کسی که در همان لحظه در دوربینِ **غیرهم‌پوشانِ** دیگری دیده می‌شود، فرد دیگری است. اگر زمان پیاده‌روی بین دوربین‌ها را تعریف کنید، پیوندهای ناممکن (خیلی زود یا خیلی دیر) رد می‌شوند. قد نسبیِ آشکارا متفاوت (بخش ۹-۵) هم پیوند را رد می‌کند.
3. **تحویل از طریق در** (`topology.doors`): وقتی کسی در دوربین B از ناحیه‌ای ظاهر می‌شود که به یک درِ دوربین A وصل است:
   - **فهرست نامزدها:** نامزدها فقط کسانی‌اند که در بازه‌ی زمانی `min_sec` تا `max_sec` قبل، از **همان در** خارج شده‌اند.
   - **یک نامزد:** همان شخص است. ظاهر فقط نباید تناقض داشته باشد (`door_min_sim`، پیش‌فرض ۰٫۵۰)، چون نور سوله و محوطه فرق دارد.
   - **چند نامزد:** ظاهر باید یکی را با فاصله‌ی روشن انتخاب کند، وگرنه تصمیم گرفته نمی‌شود.
   - **یک بار مصرف:** هر خروج فقط یک بار استفاده می‌شود.
4. **ظاهر**: شباهت گالری‌ها بالاتر از `link_threshold` (که مثل بخش ۹-۲ با یونیفرم خودکار بالا می‌رود) **و** بهتر از نفر دوم به اندازه‌ی `margin`.
5. اگر پس از `decide_after_sec` پیوند مطمئنی نبود ← **شخص جدید**. شخص جدید تا `late_merge_sec` اگر شاهد قوی‌تری رسید در شخص قبلی ادغام می‌شود.

ID محلی‌ای که هنوز به اندازه‌ی `min_obs` مشاهده‌ی تمیز ندارد (مثلاً فردی که تمام مدت با دیگری هم‌پوشانی دارد) شماره‌ی `P` نمی‌گیرد و در گزارش با `cam1:7` می‌آید؛ به‌محض رسیدن شواهد، پیوند می‌خورد.

با یونیفرم یکسان، پیوند ظاهری بین دوربین‌ها ذاتاً ضعیف‌تر از داخل یک دوربین است (زاویه و نور متفاوت). برای پیوند قابل‌اتکا: **توپولوژی و زمان عبور** را تعریف کنید و در صورت نیاز از **نشانگر کلاه/جلیقه** استفاده کنید.

```yaml
    vehicle_config: ""                         # این دوربین لیفتراک ندارد
```

ناحیه‌های `region` درِ تحویل را در **همان دوربین** با `draw_zone.py` و نوع `exit_door` بکشید. اگر اسمی در صحنه‌ی دوربین نباشد، هنگام شروع هشدار داده می‌شود.

برای **هر دوربین** کالیبراسیون و صحنه‌ی خودش را بسازید:
```powershell

python scripts/calibrate_ground_plane.py --source $src --width-m 6 --length-m 8 --out configs/cameras/cam1/calibration.yaml
python scripts/draw_zone.py --source $src --scene configs/cameras/cam1/scene.yaml --calibration configs/cameras/cam1/calibration.yaml
python scripts/draw_line.py --source $src --scene configs/cameras/cam1/scene.yaml --mode line --name gate
python scripts/diagnostic.py --cameras configs/cameras.yaml
```

### ۱۳-۴. اجرا
```powershell

python run_multi_camera.py --gui cam1         # با پنجره‌ی نمایش برای cam1
python run_multi_camera.py --only cam1 cam3   # فقط چند دوربین
```

`Ctrl+C` همه را منظم متوقف می‌کند. خروجی‌های اختصاصی هر دوربین جدا هستند: `logs/<cam>/`، `data/identity_store/<cam>/`، ضبط ویدیو در پوشه‌ی `<cam>`، و درگاه وب هر دوربین = درگاه پایه + ترتیب دوربین (۸۰۵۰، ۸۰۵۱، …).

### ۱۳-۵. نکته‌ها
- همه‌ی دوربین‌ها باید **یک مدل Re-ID** داشته باشند.
- **ساعت** سرورها باید یکی باشد (اگر دوربین‌ها روی چند کامپیوتر پردازش می‌شوند، `registry_path` و `events.db_path` روی مسیر مشترک و ساعت‌ها با NTP هماهنگ باشند).
- برای آزمایش با **فایل ویدیو**، `stream.recording_start_time` هر کلیپ را بدهید تا کلیپ‌ها در زمان هم‌تراز شوند.
- هر فرایند مدل‌های خودش را در GPU بار می‌کند؛ مصرف حافظه‌ی GPU را با `nvidia-smi` بسنجید و تعداد دوربین را با آن تنظیم کنید. برای سبک‌تر شدن: `vehicle_detect_every_n_frames: 2`، مدل اسکلت کوچک‌تر، یا `detection.imgsz` کمتر (حداقل ۱۲۸۰).

### ۱۴-۴. ویدیوی خروجی (ذخیره‌ی خودکار)

بعد از هر اجرا، ویدیوی برچسب‌خورده (جعبه‌ها، ID، منطقه‌ها، خطوط، لیفتراک و هشدارها) ذخیره می‌شود. محل ذخیره از `recording.output_video_path` تعیین می‌شود:

| مقدار | نتیجه |
|---|---|
| `auto` (پیش‌فرض) | فایل ویدیو: `outputs/<نام ویدیو>_annotated.mp4`؛ دوربین زنده: `outputs/<نام دوربین>_live.mp4` |
| یک مسیر | همان مسیر، مثلاً `runs/test1.mp4` |
| `""` | ویدیو ذخیره نشود |

```powershell
python main.py --source data/input/clip1.mp4                      # -> outputs\clip1_annotated.mp4
python main.py --source data/input/clip2.mp4                      # -> outputs\clip2_annotated.mp4 (اولی پاک نمی‌شود)
python main.py --source data/input/clip1.mp4 --output runs.mp4  # مسیر دلخواه برای همین اجرا
python main.py --source data/input/clip1.mp4 --set recording.output_video_path=   # بدون ویدیو
```

- اجرای دوباره روی **همان** ویدیو، فایل قبلی را جایگزین می‌کند؛ برای نگه‌داشتن هر دو از `--output` استفاده کنید.
- پوشه‌ی `outputs/` در git ثبت نمی‌شود.
- برای دوربین زنده حتماً قطعه‌بندی کنید:

```yaml
recording: {output_video_path: auto, segment_minutes: 15, max_segments: 96}
```
`segment_minutes: 0` یک فایل می‌سازد (مناسب کلیپ). یک فایل MP4 بی‌پایان تا بسته نشود قابل پخش نیست و دیسک را پر می‌کند. قدیمی‌ترین قطعه‌ها خودکار حذف می‌شوند.

## ۱۵. هشدارها

هر رویداد با شدت `alarm` (و رویدادهای `*_CLEARED`) به خروجی‌های هشدار می‌رود:

```yaml
alarms:
  enable_audio_alarm: true            # بوق روی همین کامپیوتر
  alarm_cooldown_sec: 5.0             # فاصله‌ی تکرار خروجی برای همان هشدار
  forward_min_severity: alarm         # alarm | warning | info
  webhook_urls: [http://siren-gateway.local/api/alarm]
  webhook_headers: {Authorization: "Bearer ..."}
  mqtt: {enabled: true, host: 192.168.1.5, port: 1883, topic: factory/alarms}
```

- **webhook**: یک `POST` با بدنه‌ی JSON (نوع، شدت، زمان، دوربین، کارگر، لیفتراک، مقدار، مسیر عکس) به هر آدرس؛ با تلاش دوباره. برای آژیر، PLC gateway، SCADA یا پیام‌رسان.
- **MQTT**: همان JSON روی `topic` (نیاز به `paho-mqtt`).
- رویدادهای `*_CLEARED` هم فرستاده می‌شوند تا آژیر بیرونی خاموش شود.
- `alarm_cooldown_sec` فقط **خروجی** را محدود می‌کند؛ **هر هشدار همیشه در پایگاه‌داده ثبت می‌شود**.

نمونه‌ی بدنه‌ی webhook:
```json
{"type": "SAFE_DISTANCE_VIOLATION_ALARM", "severity": "alarm", "wall_time": "2026-11-17 10:42:07.300",
 "camera_id": "cam1", "worker_id": 7, "worker_label": "علی رضایی", "vehicle_id": "2",
 "subject": "vehicle_2", "value": 3.85, "details": {"threshold_m": 3.0}, "snapshot_path": "data/snapshots/..."}
```

| `WRONG_WAY` | warning | عبور خلاف جهتِ مجاز |
| `DRIVER_BOARDED` | info | `how`: VISIBLE_IN_CAB / VANISHED_INTO_CAB / VEHICLE_MOVED / EMERGED_FROM_CAB؛ `reboard` |
| `DRIVER_EXITED` | info | `value` = ثانیه‌ی همان نوبت نشستن؛ `how`: VISIBLE / EMERGED_FROM_CAB |
| `DRIVER_REBOUND` | info | راننده‌ی پنهان با شماره‌ی جدید دیده شد |
| `DRIVER_SESSION_END` | info | `value` = مجموع ثانیه‌ی نشستن؛ `reason`: DRIVER_CHANGED / DRIVER_MOVED_TO_OTHER_VEHICLE / VEHICLE_LEFT_VIEW / TIMEOUT_DRIVER_AWAY / VEHICLE_MOVED_WITHOUT_DRIVER / NOT_MOVING_WITH_VEHICLE / SHUTDOWN |
| `VEHICLE_OCCUPIED_UNKNOWN_DRIVER` | info | لیفتراک با سرنشین پنهان و ناشناس |
| `SAFE_DISTANCE_VIOLATION_ALARM` | **alarm** | `value` = فاصله (متر) |
| `DRIVER_LEFT_VIEW_ALARM` | **alarm** | راننده‌ی پیاده‌شده از تصویر خارج شد |
| `DRIVER_NOT_VISIBLE_ALARM` | **alarm** | راننده‌ی پیاده‌شده مدت زیادی ناپیداست (اگر فعال باشد) |
| `DRIVER_ALARM_CLEARED` | info | `alarm_type`، `reason`، مدت هشدار |

رویدادی که `worker_id` ندارد و `track_id` دارد، برای فردی است که ID نگرفته (`details.unidentified`).

## ۱۸. ارزیابی و تنظیم

آستانه‌های پیش‌فرض با منطق و داده‌ی ساختگی تنظیم شده‌اند و **باید با ویدیوی همین کارخانه بازبینی شوند**.

### ۱۸-۱. گزارش تصمیم‌های هویتی
```powershell
python scripts/analyze_decisions.py --out logs/identity_report.txt
```
گزارش، تعداد هر نوع تصمیم، توزیع شباهت تطبیق‌های پذیرفته‌شده، ID‌های جدیدی که فرد مشابهی داشتند، بازگشت‌ها، ادغام‌ها، موارد «دو نفر بیش از حد شبیه» و در بخش ۸ **لحظه‌هایی که باید در ویدیو بررسی شوند** را می‌دهد.

| رویداد لاگ | معنی |
|---|---|
| `NEW_ID` | ID جدید (`best_existing_sim` = شباهت به نزدیک‌ترین فرد قبلی) |
| `MATCHED` | ردیاب جدید به ID موجود وصل شد؛ `stage`: STITCH، RECOVER، RECOVER_LONG، REENTRY_STRICT، BORDER_REENTRY، MARKER |
| `MATCH_REJECTED_AMBIGUOUS` / `MERGE_REJECTED_AMBIGUOUS` | رد شد چون دو نفر بیش از حد شبیه بودند |
| `EXITED` | خروج (`reason`: BORDER / DOOR / TIMEOUT) |
| `MERGED` | ID موقت با ID قدیمی یکی شد (`reason`: APPEARANCE / MARKER) |
| `BINDING_BROKEN` / `SWAP_FIXED` | ردیاب روی فرد دیگری پریده بود / جابه‌جایی دو ID اصلاح شد |
| `LABELED` / `MARKER_CONFLICT` / `MARKER_REBIND` / `MARKER_SPLIT` | رخدادهای نشانگر کلاه/جلیقه (بخش ۹-۳) |

### ۱۸-۲. مقایسه‌ی تنظیم‌ها (هر بار فقط یک تغییر)
یک کلیپ ۳ تا ۵ دقیقه‌ای انتخاب کنید که خروج و ورود دوباره، عبور از کنار هم، و سوار/پیاده‌شدن راننده داشته باشد و «واقعیت» آن را یادداشت کنید (تعداد افراد، زمان هر خروج/ورود، هر سوار/پیاده‌شدن).

```powershell
function Run-Exp([string]$Name, [string[]]$Extra = @()) {
  $common = @("--no-gui",
    "--set", "recording.output_video_path=runs/$Name.mp4",
    "--set", "reid.decision_log_path=runs/${Name}_decisions.jsonl",
    "--set", "events.db_path=runs/${Name}_events.db",
    "--set", "events.csv_dir=runs/${Name}_csv",
    "--set", "events.snapshot_dir=runs/${Name}_snap",
    "--set", "stream.recording_start_time=2026-01-01 08:00:00")
  python main.py --source data/input/clip1.mp4 @common @Extra
  python scripts/analyze_decisions.py --log "runs/${Name}_decisions.jsonl" --out "runs/${Name}_identity.txt"
  python scripts/report.py --db "runs/${Name}_events.db" --date 2026-01-01 --registry none --out "runs/${Name}_report"
}

Run-Exp base
Run-Exp ocsort     @("--set", "detection.tracker_config=configs/trackers/factory_ocsort.yaml")
Run-Exp deepocsort @("--set", "detection.tracker_config=configs/trackers/factory_deepocsort.yaml")
Run-Exp tracktrack @("--set", "detection.tracker_config=configs/trackers/factory_tracktrack.yaml")
Run-Exp pose_x     @("--set", "detection.model_weights=yolo11x-pose.pt")
Run-Exp ain        @("--set", "reid.model_name=osnet_ain_x1_0", "--set", "reid.weights_path=weights/osnet_ain_x1_0_msmt17.pt")
Run-Exp uniform    @("--set", "reid.head_branch_weight=0.45", "--set", "reid.color_branch_weight=0.10")
```

| ستون مقایسه | از کجا |
|---|---|
| تعداد کل ID (در برابر تعداد واقعی) | `runs/<name>_identity.txt` بخش ۱ |
| بازگشت درست / ID اشتباه / ID جدید برای فرد برگشتی | همان گزارش بخش‌های ۴ و ۸ + دیدن همان لحظه در ویدیو |
| راننده‌ی درست، هشدار درست | `runs/<name>_report/forklift_sessions.csv` و `alarms.csv` |
| FPS | نوار بالای ویدیو |

**قاعده‌ی تصمیم:** «ID اشتباه» از «ID جدید» بدتر است. گزینه‌ای برنده است که ID اشتباه کمتری دارد و FPS‌اش قابل‌قبول است.

## ۱۹. استقرار ۲۴ ساعته

**چک‌لیست پیش از بهره‌برداری**
1. `python scripts/diagnostic.py` بدون `FAIL`.
2. کالیبراسیون هر دوربین با یک فاصله‌ی معلوم روی زمین کنترل شده باشد.
3. مدل اختصاصی لیفتراک نصب و روی تصاویر همین کارخانه آزموده شده باشد.
4. آستانه‌ها با روش بخش ۱۸ روی ویدیوی واقعی بازبینی شده باشند.
5. سیاست هشدار با مسئول ایمنی نهایی شده باشد و خروجی هشدار (آژیر/webhook) آزمایش شده باشد.
6. `display_gui: false`، `recording.segment_minutes` غیرصفر، `events.retention_days` متناسب با سیاست نگهداری.

**اجرا به‌صورت سرویس**
```powershell
python main.py --no-gui --restart-on-failure           # یک دوربین
python run_multi_camera.py                              # چند دوربین (ناظر، هر دوربین را جدا راه‌اندازی دوباره می‌کند)
```
برای شروع خودکار با ویندوز از Task Scheduler («At startup»، با همان محیط Python و پوشه‌ی کاری پروژه) یا یک مدیر سرویس مثل NSSM استفاده کنید.

**پایش سلامت:** فایل `logs/heartbeat.json` هر ۵ ثانیه نوشته می‌شود (FPS، اتصال دوربین، تعداد اتصال دوباره، ثانیه از آخرین فریم، خطاهای پیاپی، رویدادهای نوشته‌شده، هشدارهای فعال). اگر زمان تغییر این فایل قدیمی شد، فرایند گیر کرده است. همین اطلاعات از `/api/status` هم در دسترس است.

**رفتار در خطا**
- قطع دوربین: اتصال دوباره با تأخیر افزایشی؛ برنامه خارج نمی‌شود (مگر `stream.max_stall_sec`).
- خطای یک فریم: ثبت در لاگ و ادامه؛ پس از `max_consecutive_errors` خطای پیاپی خروج (و با `--restart-on-failure` ساخت دوباره).
- کندی دیسک: نوشتن رویدادها در رشته‌ی جدا؛ اگر صف پر شود هم‌زمان نوشته می‌شود و **هیچ هشداری دور ریخته نمی‌شود**.

| `... do not fit model ...` | فایل وزن متعلق به مدل دیگری است. |
| `settings: unknown key '...' (typo?)` | نام کلید را با `configs/settings.yaml` مقایسه کنید. |
| `... must be float, got str` | نوع مقدار در YAML اشتباه است. |
| `Invalid scene definition` | یک چندضلعی کمتر از ۳ نقطه دارد یا خطی ناقص است؛ با ابزار رسم دوباره ذخیره کنید. |
| `No ...calibration.yaml: metric distances are NOT valid` | بخش ۶ انجام نشده. |
| `Vehicle classes ... not in the vehicle model` | نام کلاس در `vehicle_class_names` با مدل جور نیست؛ نام‌های موجود در همان پیام آمده‌اند. |

| تصویر RTSP خاکستری/کشیده | `stream.rtsp_transport: tcp` |
| FPS پایین | CUDA فعال باشد؛ `vehicle_detect_every_n_frames: 2`؛ مدل اسکلت کوچک‌تر؛ `display_gui: false`. |
| افراد دور ID نمی‌گیرند | crop خیلی کوچک است؛ مدل اسکلت بزرگ‌تر یا `imgsz` بیشتر. |

TIMEOUT` بگردید. |
| کارگر هم‌لباسی که قبلاً پشت کامیون بوده، ID فرد پنهان را می‌گیرد | با ظاهر به‌تنهایی جداشدنی نیست. اگر قدشان حدود ۸ سانتی‌متر یا بیشتر فرق کند، `BINDING_BROKEN` با `reason: STATURE` در لاگ می‌آید. در غیر این صورت: آموزش مدل روی ویدیوی خودتان (بخش ۹-۶)، نشانگر کلاه یا جلیقه، یا دوربین دوم. |
| `STATURE_VETO` در لاگ زیاد است | دو نفر با قد آشکارا متفاوت رد شده‌اند و این رفتار درست است. اگر برای یک نفر رخ می‌دهد (مثلاً روی سطح شیب‌دار یا پله)، `reid.stature.min_diff` را بیشتر کنید یا `enabled: false`. |
| ID فردی که کاملاً دیده می‌شود (یا پشت ماشین رفته) عوض می‌شود | نسخه‌های قدیمی: هویتی که کنار دیگران ساخته می‌شد گالری ظاهر نداشت و با دور‌شدن از آن‌ها ID جدید می‌گرفت؛ در نسخه‌ی جاری رفع شده است. اگر ادامه داشت `logs/identity_decisions.jsonl` را بررسی کنید (بخش ۱۸-۱). |
| ویدیوی خروجی ذخیره نشد | لاگ را برای `Annotated video will be saved to ...` ببینید؛ `recording.output_video_path` خالی نباشد؛ پوشه‌ی `outputs\` را بررسی کنید؛ برنامه با خطا بسته شده باشد، فایل تا همان لحظه ذخیره است. |
| یک نفر دو ID پشت سر هم | گزارش بخش ۱۸-۱ (بخش‌های ۳ و ۸)؛ ردیاب‌های دیگر را بیازمایید. |
| شمارش خط دو برابر یا صفر | جهت خط (`invert`) و `dead_band_px` را بررسی کنید؛ خط را جایی بکشید که **نقطه‌ی پا** از آن می‌گذرد، نه بالاتنه. |
| هشدار فاصله‌ی غلط | کالیبراسیون را کنترل کنید؛ رد کف لیفتراک روی تصویر را ببینید؛ `vehicle_depth_m` را با طول لیفتراک تنظیم کنید. |
| راننده‌ی سقف‌دار «ناشناس» می‌ماند | او هیچ‌وقت بیرون کابین دیده نشده؛ با پیاده‌شدنش شناخته می‌شود. نشانگر کلاه یا دوربینی که داخل کابین را ببیند کمک می‌کند. |

| `web.enabled` ولی صفحه باز نمی‌شود | `pip install fastapi uvicorn`؛ درگاه و `token`. |

## ۲۲. محدودیت‌ها، مجوزها، ایمنی و حریم خصوصی

**محدودیت‌های فنی**
- **یونیفرم یکسان:** تشخیص هویت فقط با ظاهر، وقتی همه لباس مشابه دارند و تصویر دور است، ذاتاً نامطمئن است. سامانه طوری ساخته شده که در تردید ID جدید بدهد. برای بازگشت‌های طولانی و برای چند دوربین، هویت قابل‌اتکا به **نشانگر کلاه/جلیقه** (یا اتصال به سامانه‌ی تردد) نیاز دارد.
- **آستانه‌ها** باید با ویدیوی واقعی همین کارخانه بازبینی شوند (بخش ۱۸).
- **مدل لیفتراک** باید اختصاصی آموزش داده شود (بخش ۱۲-۱).
- **فاصله‌ی متری** فرض می‌کند زمین صاف است و کالیبراسیون درست؛ رد کف لیفتراک تقریبی است (خطا در حد چند ده سانتی‌متر تا حدود نیم متر، بسته به زاویه).
- **راننده‌ی کاملاً پنهان** فقط با قرائن (ناپدیدشدن کنار کابین، حرکت لیفتراک، ظاهرشدن کنار آن) شناخته می‌شود.
- **پیوند بین دوربین‌ها** با ظاهرِ تنها ضعیف‌تر از داخل یک دوربین است.

**مجوزها (پیش از استفاده‌ی تجاری با واحد حقوقی بررسی شود)**
- **Ultralytics YOLO** مجوز AGPL-3.0 دارد؛ استفاده‌ی تجاری بسته معمولاً مجوز Enterprise یا رعایت AGPL می‌خواهد.
- وزن‌های **OSNet** روی مجموعه‌داده‌ی MSMT17 آموزش دیده‌اند که برای پژوهش غیرتجاری منتشر شده است.

**ایمنی و حریم خصوصی**
- این سامانه **تجهیز ایمنی گواهی‌شده نیست** و جایگزین حفاظ فیزیکی، رویه‌ها و آموزش نمی‌شود؛ یک سامانه‌ی **کمکی** هشدار است. نبودِ هشدار به معنی ایمن بودن نیست.
- ضبط و ردیابی تصویر کارکنان باید مطابق قوانین و سیاست سازمان باشد: اطلاع‌رسانی، محدودیت دسترسی، مدت نگهداری (`events.retention_days`، قطعه‌های ویدیو، `data/snapshots/`).
- `configs/workers.yaml` (نام کارکنان) و `configs/cameras.yaml` (رمز دوربین‌ها) در git ثبت نمی‌شوند؛ دسترسی به آن‌ها و به پوشه‌ی `data/` را محدود کنید.

## ۲۳. تغییرات نسبت به نسخه‌ی قبلی

**اشکال‌های برطرف‌شده**
- ساختن «مچ پای مصنوعی» برای هر فردی که پاهایش دیده نمی‌شد (که عابرِ پشت پالت را «راننده‌ی نشسته» می‌کرد و کنترل «فاصله‌ی نامطمئن» را از کار می‌انداخت) حذف شد.
- فاصله‌ی راننده تا لیفتراک دیگر نقاطی را که روی زمین نیستند از هموگرافی کف عبور نمی‌دهد.
- هشدارهایی که در بازه‌ی سکوت بوق می‌افتادند دیگر از ثبت حذف نمی‌شوند.
- بازیابی راننده با شباهت ظاهری ضعیف (که با یونیفرم تقریباً با هر کسی جور می‌شد) حذف شد.
- راننده‌ی پنهان زیر سقف دیگر «فاصله‌ی نامطمئن» و لیفتراکِ در حرکت دیگر «پارک، بدون راننده» نشان داده نمی‌شود.
- راننده‌ی پیاده‌شده‌ای که در تصویر از جلوی لیفتراکش رد می‌شد فوراً «سوار» حساب می‌شد؛ اکنون تأیید می‌خواهد.
- راننده‌ی جدید روی لیفتراکی که راننده‌ی قبلی‌اش ثبت بود شناخته نمی‌شد.
- بازیابی پس از پنهان‌شدن، فرد برگشتی را با همکارِ شبیهِ پنهان‌شده اشتباه می‌گرفت چون با افرادِ خارج‌شده مقایسه نمی‌کرد.
- عبور از خط با لرزش نقطه‌ی پا چند بار شمرده می‌شد؛ خروج از درِ داخل منطقه‌ی جهت‌دار شمرده نمی‌شد.
- زمان حضور در منطقه در هر ورود بازنویسی می‌شد (جمع نمی‌شد).
- خواندن RTSP در قطعی دوربین بی‌صدا متوقف می‌ماند؛ یک خطا کل برنامه را می‌بست؛ ID‌ها پس از ری‌استارت از ۱ شروع می‌شدند.
- دانلود وزن Re-ID فقط به Google Drive وابسته بود.
- هویتی که هنگام حضور کنار دیگران ساخته می‌شد گالری ظاهر نداشت؛ شباهتش روی ۰٫۰۷ می‌ماند و با دور‌شدن از دیگران، ID فرد کاملاً دیده‌شده عوض می‌شد. اکنون از اولین تصویر تمیز گالری ساخته می‌شود.
- لیفتراک به‌عنوان مانع شناخته می‌شود: تصویر فردی که بخش بزرگی از او پشت لیفتراک است برای ظاهر ذخیره نمی‌شود و اتصال را نمی‌شکند؛ سخت‌گیری بازیابی پس از پنهان‌شدن طولانی کمتر شد (`recover_strict_after_sec` از ۴ به ۸ ثانیه).
- ویدیوی خروجی با نام ثابت در پوشه‌ی اجرا نوشته و در اجرای بعدی بازنویسی می‌شد.
- فردی که پشت کامیون یا دستگاه می‌رفت با ID جدید برمی‌گشت. علت‌ها:
  - پس از ۲۰ ثانیه «خارج‌شده» حساب می‌شد.
  - بیرون‌آمدن در انتهای کامیون (دورتر از ۵٫۵ متر) ناممکن حساب می‌شد.
  - همکاران هم‌لباسی که جای دیگری دیده می‌شدند یا رفته بودند، بازیابی را «مبهم» می‌کردند.
  - ID جدید از تصویرهای نیمه‌پنهان ساخته می‌شد.
  - ادغام خودکار بدون بررسی ابهام، دو نفرِ پشت یک کامیون را جابه‌جا می‌کرد.

**قابلیت‌های جدید (این مرحله)**
- **قد نسبی:** خودآموز و مستقل از یونیفرم، برای رد کردن پیوندها داخل یک دوربین و بین دوربین‌ها. بازیابی پس از پنهان‌شدن تا اندازه‌گیری قد موقت می‌ماند.
- **تحویل از طریق در** بین دوربین‌های بدون هم‌پوشانی (`topology.doors`).
- **ابزار آموزش مدل ظاهر روی ویدیوی خودتان:** `mine_reid_data.py` و `train_reid.py`، با سنجش قبل و بعد.
- **ابزار ساخت داده و آموزش مدل لیفتراک:** `prepare_vehicle_dataset.py` و `train_vehicle_model.py`.
- **نشانگر روی جلیقه:** ناحیه‌ی تنه (سینه و پشت) هم خوانده می‌شود، و `make_markers.py --distance-m` اندازه‌ی لازم برای دوربین شما را حساب می‌کند.
- **رفع اشکال نشانگر:** نشانگری که روی ردِ بازیابی‌شده پس از پنهان‌شدن خوانده شود، دیگر به سابقه‌ی فرد پنهان نسبت داده نمی‌شود و آن فرد را با هویت دیگری ادغام نمی‌کند.

**قابلیت‌های جدید**
آستانه‌ی خودتنظیم یونیفرم، نشانگر کلاه، درهای داخل تصویر، ماندگاری هویت، منطقه‌ی ممنوعه و سقف حضور/ظرفیت، مسیر یک‌طرفه، انتساب دیرهنگام رویداد، لیفتراک سقف‌دار، جلسه و زمان نشستن راننده، هشدار خروج راننده از تصویر، پایگاه‌داده‌ی یکپارچه‌ی رویداد و گزارش کارگر، webhook / MQTT، API وب، heartbeat، ضبط قطعه‌قطعه، اعتبارسنجی تنظیمات، `--set`، **چند دوربین با شماره‌ی شخص مشترک**، ذخیره‌ی خودکار ویدیوی خروجی برای هر ورودی (`--output`).

**تغییرهای ناسازگار**
- شکل‌ها از `settings.yaml` به `configs/scene.yaml` رفته‌اند (تعریف‌های قدیمی هنوز خوانده می‌شوند).
- `system.output_video_path` به `recording.output_video_path` منتقل شد (نام قدیمی هنوز پذیرفته می‌شود).
- پیش‌فرض `recording.output_video_path` از `output_industrial_reid.mp4` به `auto` تغییر کرد (`outputs/<نام ویدیو>_annotated.mp4`).
- تنظیم‌های لیفتراک از «تعداد فریم» به «ثانیه» تغییر کرده‌اند (`entry_confirmation_frames` ← `board_confirm_sec` و …).
- رویدادهای لیفتراک به‌جای `data/vehicle_safety_events.*` در `data/factory_events.db` ثبت می‌شوند؛ نام فیلد `event_type` به `type` تغییر کرده است.
- ماژول‌های `app/zones`، `app/logic/state_machine.py`، `app/logic/directional_tracker.py` و `app/vehicle_monitoring/alarm_and_logger.py` با `app/analytics` و `app/core` جایگزین شده‌اند.
